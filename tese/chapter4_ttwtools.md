# 4 TTWtools

## 4.1 TTWtools: Introduction and Motivation

TTWtools was born out of the need to annotate and count tags in a corpus and to compare corpora using KFA. In the first year of my doctoral period, our research group was working on the functional analysis of features from a KFA of a corpus of Agrarian Sciences articles. For this work, we had a dataset containing the counts of all tagged features in each text of the corpus.

To analyze the use of those features in the texts, we had to search the dataset for the texts in which a feature had a high **d** value, record the filenames of those texts, find these texts in the corpus folder, and finally look for the features and select examples. This process took time, and I began to think about how to automate it. During this period, I was also looking for freely available taggers and learning how to use them and how to use Python to count the tags, calculate Cohen’s **d** values for the KFA, and plot the bar charts. At the time, I had just started learning Python, and these tasks were challenging.

After I was able to perform these tasks with Python and a few command-line tools, I realized that the process could be improved further. I wanted to put all the necessary steps for a KFA, from tagging to functional analysis, in one place. I also wanted it to be a graphical user interface (GUI) tool so that other researchers and students with limited programming skills could use it. That was when I started developing TTWtools with the assistance of a more experienced programmer. The first version did exactly that: it integrated a set of taggers and KFA functions into a single interface. The taggers already included BiberPlus with spaCy, MFTE with Stanza, and spaCy and Stanza as standalone taggers.

Once the first version was ready and working, its limits became clear. It solved the manual KFA workflow, but it was still a KFA tool. It always started from a pair of corpora, worked only in English, and its main analysis depended on Biber’s taxonomy. It had no ready corpora, no search, and no KWIC. The project files were large, and the annotation was a block that did not tell me which tagger, model, or configuration had produced a number. These limits shaped the next design.

We then started thinking about other improvements. We decided to make the tool bilingual and to make it possible to incorporate taggers for other languages. We also began introducing other traditional corpus linguistics analyses, such as frequency lists, KWIC, and collocations. The idea of including a learning module came from the need to understand the statistics of KFA and other metrics. The learning module was used in the classes reported in Chapter 7.

There are still several improvements to make and ideas to explore in TTWtools. One is a more robust version of KFA. Another is the development of the Writing module, a corpus-based tool to help Brazilian learners improve their writing in English and to help teachers assess student writing. An experimental Writing area already exists, but the fuller module will require further research in statistics and is planned for the coming years. The catalog mechanism for reference corpora also exists, but there is no public catalog of reference corpora yet, and large reference corpora at the scale of the BNC or Hansard are not supported as full corpora. Reference frequency lists provide a partial path for keywords and bands, but they still depend on preparing and distributing the list.

This experience illustrates a broader problem. Corpus linguistics and descriptive linguistics depend on tools. A concordance, a frequency list, a measure of dispersion, or a comparison between corpora is not only a calculation. It is a way of making a linguistic question operational. The choice of tool affects which questions can be asked, which data can be inspected, and how results can be reported. A tool that hides its assumptions or its annotation decisions can produce numbers that look precise but cannot be interpreted. Command-line tools and programming libraries offered control and reproducibility, but they required programming skills. Graphical interfaces offered accessibility, but they often limited the analyses or hid the annotation layer. When I started, the available options required a choice between these two paths. I wanted a local application that offered the accessibility of an interface without giving up the methodological control of a scriptable tool.

Annotation raised a second problem. A corpus can be annotated by different taggers, and these taggers do not tokenize or tag in the same way. One tagger may split contractions, another may keep them; one may use a universal tag set, another may use a language-specific inventory. If the tool treats annotation as a single invisible layer, the user cannot tell which decisions produced a count. TTWtools treats each annotation as a separate layer, with its tagger, version, model, and configuration. Layers can coexist over the same text, and each analysis records the layer it used. This design supports comparison and reanalysis and prevents the corpus from being retagged without need.

Exploration and comparison raised a third problem. Research and teaching often begin with a word, a phrase, or a pattern in context. They continue with frequency, dispersion, and collocation. They may end with a comparison between corpora, between groups, or between a single text and a reference. Many tools support one part of this path but not the others. TTWtools connects the parts. A query can be inspected in KWIC, counted, placed in its dispersion, compared with a reference, and opened in the Reader. The same project holds the texts, the layers, and the results.

Reproducibility and privacy raised a fourth problem. Corpora used in teaching and research often contain student essays, interviews, classroom transcripts, or other material that cannot be sent to an external service. Local processing is therefore not only a technical preference. It is a condition for using the tool with sensitive data. A result should also be more than a screenshot. It should be possible to know which corpus, which layer, which parameters, and which version produced it. TTWtools stores analyses with their parameters and the layers they used. It also provides a Copy as code action that produces the equivalent command line and Python snippet. This does not make every analysis reproducible in an absolute sense, because models and libraries change. It does make the path from a result to its conditions visible.

The tool is designed for corpus linguistics and descriptive linguistics, especially for students, and it is also meant to be accessible to teachers who want to produce data-driven learning (DDL) materials. For corpus linguistics, it offers exploration and comparison with explicit annotation layers. For descriptive linguistics, it offers close reading of texts with tags, concordances, and contextual examples. The same interface serves teaching, where the Learn area explains concepts, metrics, and screens, and research, where the project file and the command line support documentation and reanalysis.

TTWtools is a local application. It runs on the user’s computer, keeps the texts and results in a project file, and does not send the corpus to a remote service during analysis. It integrates existing language-processing libraries, including spaCy, Stanza, BiberPlus, and MFTE. It does not replace these libraries or treat their output as a definitive analysis. The quality of annotation depends on the model, the language, the genre, and the configuration. The interface and the help material state this, and each layer records the conditions under which it was produced.

The description refers to application version 0.8.3 and package version 0.3.1. Section 4.2 describes how the tool is built and how it works: the project as a database, the annotation layers, the storage formats, the search index, the execution model, and the use of AI agents in development. Section 4.3 describes the functions from the user’s point of view: projects and corpora, tagging, exploration, comparison, Writing, help, resources, and automation.

The contribution of the chapter is twofold. It documents a tool that connects exploration, comparison, and reproducibility in a local environment. It also describes the design decisions behind that tool, so that results produced with it can be read with an understanding of their conditions. The chapter begins this description with the scope of the work and the principles that organize the project.


## 4.2 How TTWtools Is Built and How It Works

### 4.2.1 Scope and Purpose

This section describes how TTWtools is built and how it works. It aims to explain what the tool stores, what it calculates, and what it assumes about language data. The design documents of the project are used as a source for intentions and justifications, but the object of description is what exists in the code and in the tests.

TTWtools is a local corpus analysis application. “Local” means that the program, the texts, the annotations, and the results remain on the user’s computer. No text is sent to an external service, and no account on a website is required. The application supports four groups of operations: (1) organizing texts in a project, (2) annotating them with language-processing libraries, (3) exploring them through searches and concordances, and (4) comparing them with other corpora. The same logic that serves the graphical interface is also available as a Python library and, for most operations, as a command-line interface. This equivalence is a design decision, not a technical detail: an operation performed through the interface can be repeated, documented, and automated with the same parameters.

For a practical purpose, the relevant question is not which programming language the tool uses. The relevant question is what the tool stores, what it calculates, and what it assumes about the data. This text addresses those questions. Technical terms are explained when they first appear, and analogies are used only when they clarify an idea.

### 4.2.2 Design Principles

Six principles shape the tool.

First, the processing is local. The texts, the annotations, and the results stay on the user’s computer; the application does not need an internet connection to analyze a corpus, and no text is sent to a remote server. Annotation models are downloaded only by explicit choice. This matters especially when the corpus contains student essays, interviews, or other sensitive material.

Second, the graphical user interface (GUI) is meant to be accessible and intuitive: users explore, compare, and analyze corpora through menus, buttons, visualizations, and tables, with frequent operations in the foreground and specialized settings in panels that can be expanded on demand. Most of these operations are also available through a command-line interface (CLI) and a Python library, so that an analysis made on screen can be repeated, documented, and automated. The interface is also multilingual by design: its texts, the help topics, and the descriptions of taggers and tags are stored as translation entries, separate from the code, so that new languages can be added without changing the program. Portuguese and English are currently available.

Third, the tool behaves equivalently across operating systems and architectures. TTWtools runs on Linux, macOS, and Windows, on both Intel and Apple Silicon processors, and projects and results do not depend on the system on which they were produced. A corpus prepared on one computer can therefore be analyzed on another.

Fourth, the tool integrates well-established libraries of specialized use and makes it possible to use them in an accessible and combined way. Python libraries such as spaCy, Stanza, MFTE, and biberplus are brought together in TTWtools and can be applied through the graphical interface, in the same environment and on the same corpus. The options of each tagger are presented with explanations, and the results are stored in the project in a common form. This makes these libraries easier to use for researchers, teachers, and students with no prior programming experience.

Fifth, a single corpus can hold several layers and annotations. The output of different taggers and methodologies is stored side by side, as separate layers over the same texts, and each layer is computed once and reused by every analysis, which keeps storage compact and processing efficient. Because all layers refer to the same documents, the user can compare taggers and analytical approaches on identical material, without duplicating the corpus or repeating annotation work.

Sixth, projects are portable and meant to last. A project should open on another computer, be archived, be shared with a colleague, or be reopened years later. For this reason, the project file is an open format, documented and readable without the application, and it relies only on standard-library resources. Tables and data can also be exported to a variety of formats (such as CSV, JSONL, Parquet, CoNLL-U, and VRT), so that results can be analyzed in other software, archived, or published (Section 4.2.7).

### 4.2.3 Overall Architecture

The architecture has three main components, which work on a project file, as shown in Figure 4.1. The first is the graphical interface, written with Vue 3, a JavaScript library for building interfaces. It contains the menus, forms, tables, charts, and the annotated-text reader. The second is the local server, written in Python with the FastAPI framework, a library that organizes communication between programs. The server receives requests from the interface, coordinates long tasks, and returns structured results. To carry out the operations, it calls the third component, the Python package `ttwtools`, which contains the functions that read texts, run the taggers, query annotations, calculate statistics, and generate chart data. The package also defines and maintains the file formats used by the project. The results of these operations are kept in the project file, an SQLite database that stores texts, metadata, annotation layers, and analysis results. 

The separation between interface and server is not only organizational. It allows the same analysis core to be used in a native desktop window, in a browser pointed at the local server, or, without any interface, on the command line and in research scripts. The application can run in desktop mode, with its own window, or in local web mode. In both cases, the server and the package are the same.

The `ttwtools` package is the analytical core. It is organized into modules, separate parts of the program with distinct responsibilities: text and metadata import; simple tokenization; definition and storage of annotation layers; connectors for taggers; queries (search, concordance, frequency, collocates, and dispersion); keywords; feature tables and KFA; descriptive statistics; visualization data; corpus catalog; input and output formats; help; and generation of equivalent code. This division supports maintenance and makes explicit where each calculation takes place.

The help system is part of the architecture. Explanatory texts about concepts, metrics, and screens are stored as plain-text files with light formatting (Markdown) by language, with a title, a summary, and links to related topics. The same content feeds the explanation tooltips, the guided tours, the Learn screen, and the `ttwtools help` command. Explanation is therefore treated as data, separate from the interface code, rather than as an appendix added after development.

### 4.2.4 The Project as a Database

A TTWtools project is a single file, built on SQLite, a database system that keeps an entire database in one file and needs no separate server. It works like a spreadsheet workbook: one file with several related tables, in which the texts, the metadata, the annotation layers, and the saved analyses are linked to each other. This format ensures integrity, because documents, layers, and tokens are related through identifiers and no layer can exist without its document; speed, because indexes locate a word or tag among millions of tokens without reading the whole file; and safety, because opening a database does not run embedded code, unlike spreadsheets with macros or Python `pickle` files.

The standard project, `.ttwa`, keeps everything in one file. The lighter `.ttwl` variant keeps the texts in a folder next to the file, which suits large corpora, and `.ttwc`, `.ttwcl`, and `.ttwal` hold a single corpus or a selection of corpora for sharing (Section 4.3.2). Files are compressed without loss of information to save space, and the `.ttwt` format is the compressed version used for sending and archiving.

Inside the project, the information is organized in separate, related entities: documents, layers, and tokens. Each document records its filename, its corpus, its metadata (such as level, author, year, or genre), and a fingerprint of its content, a short code calculated from the text that changes if a single character changes. The fingerprint allows the application to detect that a text has been modified since it was annotated and to recognize identical texts. An annotation layer is the result of one tagger applied to one document, and it refers to the text by character positions (a standoff representation) instead of altering it. Because layers are separate from the text, the same document can have, for example, a spaCy layer and a BiberPlus layer, or an old and a new layer, without duplicating the text or mixing the analyses.

Each layer records the tagger, its version, the model, and the options that affect the result. Before annotating, the application looks for a layer that already satisfies the request and reuses it, so that documents that were already annotated are not processed again, even if a process is interrupted. The saved analyses (such as KFA, frequencies, or collocates) are stored with their parameters and the layers they used, which documents how a result was obtained and allows it to be reused while texts, layers, and parameters remain unchanged. Analyses made in the interface can also be exported as an equivalent command and Python snippet, so that they can be repeated outside it, although full reproducibility still depends on the versions of models and libraries, which the project records.

To keep files small and queries fast, the tokens of each layer are stored in a compact columnar format called TCL (*TTWtools Columnar Layer*). Instead of repeating each word, lemma, and tag millions of times, the format keeps a lexicon of the corpus and stores the layer as sequences of identification numbers, which are then compressed. Searches are accelerated by indexes, which work like the index of a book. In projects saved without search tables, to be smaller, the index is built in a cache folder the first time it is needed, so that the project opens quickly and only the first search may take a few extra seconds. The application can read earlier versions of the format, so that older projects remain accessible.

### 4.2.5 Corpora, Documents, and Metadata

A **corpus** in TTWtools is a set of documents grouped under a name inside the project. A project can contain several corpora, such as “essays,” “articles,” and “reference,” and each analysis chooses which corpus to use. This organization allows different corpora to be compared without mixing their texts.

Import accepts a folder of `.txt` files, a single file, a CSV file (a text file with comma-separated values) with a text column, or text pasted into the interface. Metadata can come from filenames or from a separate CSV file. The application shows a preview of how filenames will be interpreted before importing, which reduces metadata coding errors. A name such as `student_B1_2024.txt`, for example, can be read as three fields: student, level, and year.

In addition to plain text, TTWtools imports annotated formats: CoNLL-U, the column format of Universal Dependencies; the `word/TAG` format used by corpora such as Brown and LOB; TEI P5 and BNC XML, standards for encoding digital texts; and GrAF, a standoff format used by corpora such as OANC and MASC. In these cases, the existing annotation is converted into a layer and the text is preserved. This allows annotated corpora to be analyzed without retagging every text.

Simple tokenization, performed without a tagger, splits the text into units using regular expressions, which are patterns of characters. It is used in statistics that do not depend on part of speech and is explicitly an **estimate**. A tagger may split contractions, punctuation, and compound words differently. The application states this in the interface. When a layer is selected, the statistics use that layer’s tokenization, and the numbers may change slightly. This transparency prevents estimates from being treated as definitive measurements.

Metadata supports filters and groups. A metadata filter selects documents, and a metadata grouping creates the groups to be compared. This mechanism allows KFA to compare “B1” with “C1” inside the same corpus, or the Lab to compare several proficiency levels at once.

### 4.2.6 Tagging and Layers

Tagging, in TTWtools, means assigning to each token of a text one or more linguistic descriptions: part of speech, lemma, a tag from the tagger’s tag set, and, in some cases, morphological information. In this chapter, “feature” refers to the linguistic variables used in Biber-style analysis and in KFA.

Tagging depends on tokenization. Different taggers tokenize differently. Some split “don’t” into “do” and “n’t,” while others keep the contracted form. Some treat punctuation as a token, while others do not. For this reason, layers align with the text by character position rather than by token number. This decision allows layers that tokenize differently to be compared without losing the reference to the original text.

Currently, TTWtools integrates four families of taggers, summarized in Table 4.1. All produce the same output format, so later analyses do not need to know which tagger generated a layer.

**Table 4.1: Integrated taggers**

| Tagger | Nature | What it produces | Languages | Notes |
|---|---|---|---|---|
| spaCy | Trained statistical and neural models | Tokenization, part of speech, lemma, morphology | English and Portuguese | Models of different sizes, downloaded on demand |
| Stanza | Trained neural models aligned with Universal Dependencies | Tokenization, part of speech, lemma, morphology | English and Portuguese | Also used as a tokenizer by other taggers |
| BiberPlus | Rules applied over spaCy’s tokenization and part-of-speech tags | About 67 Biber features | English | Requires spaCy and an English model |
| MFTE | Tagger based on Stanza and torch (a machine-learning library) | Extended set of features, with an extended version | English | Optional and heavier dependency; separate license |

Each tagger brings its own characteristics, limitations, and biases, and the distinction between trained models and rules matters for interpretation. spaCy and Stanza are machine-learning systems. Their decisions come from statistical patterns learned from annotated data, so they can make systematic errors, and their quality depends on the model, on how similar the analyzed texts are to the data used in training (in genre, register, and variety of the language), and on the language itself. Texts from learners, informal writing, or historical varieties, for example, may be tagged less accurately than the standard written texts on which such models are usually trained. The two systems also differ from each other in tokenization, in the tag sets they use, and in the size and type of models available.

BiberPlus and MFTE work differently, because they identify linguistic features, not just parts of speech. 

BiberPlus implements the set of features associated with Biber’s tradition. It runs on a spaCy pipeline, which provides the tokenization and the part-of-speech tags, and then applies explicit rules to those tags to identify each feature. The rules make it more predictable and easier to inspect, but they reflect the decisions made when they were written, they can only find what they anticipate, and they inherit the errors of the spaCy model underneath. 

MFTE (Multi-Feature Tagger of English) follows the same logic with a broader set of features, including an extended version. It runs on Stanza instead of spaCy, so its results depend on that model as well as on its own feature definitions. 

BiberPlus and MFTE are both limited to English.

Thus, none of these taggers is neutral. Each carries a conception of what a token is, which parts of speech exist, and which features are worth identifying, and these conceptions shape the counts that later analyses produce. The same text can yield different numbers depending on the tagger, the model, or the version used. For this reason, TTWtools does not treat the output of a tagger as a definitive analysis. It records which tagger, version, model, and configuration produced each layer, and it allows layers from different taggers to be compared over the same texts, so that the effect of these choices can be examined rather than ignored.

The application offers configuration presets: **Fast**, **Recommended**, and **Most accurate**. The presets fill in the tagger options. The **Customize** panel exposes the options with explanations and indicates which options change the result and which affect only performance. The **tag set** of each tagger can be consulted with definitions and examples, and the same content feeds the help system and the reader. The goal is for users to know what a tag means before interpreting a count.

Layer reuse was described in Section 4.2.4. Its effect on the workflow deserves attention. The tagging screen allows the user to build a list of steps to run, for example basic statistics, a spaCy layer, and a BiberPlus layer, and then run everything at once. The application calculates only what is missing. If the list is interrupted, completed work remains; when the user resumes, the application does not repeat what already exists.

This design matters for large corpora and slow machines. It also makes work incremental. A user can start with a light layer, explore the corpus, and later add a more expensive layer only for the analysis that requires it. The tool does not require a complete annotation before any exploration.

### 4.2.7 Import, Export, and Interoperability

TTWtools is designed to be interoperable. It reads a diversity of formats used in corpus linguistics and natural language processing, from plain text to annotated and standoff corpora, and it exports texts, annotation layers, and result tables to formats that other software can open. This compatibility allows TTWtools to be one step in a larger workflow, combined with resources and programs developed elsewhere. Table 4.2 summarizes the main formats.

**Table 4.2: Input and output formats**

| Format | Input | Output | Typical use |
|---|---|---|---|
| Plain text (`.txt`, folder, CSV) | Yes | Texts next to the project | Personal corpora, essays, interviews |
| CoNLL-U | Yes, with layer | Yes | Universal Dependencies, exchange with other software |
| `word/TAG` (Brown, LOB) | Yes, with layer | No | Historical annotated corpora |
| TEI P5 and BNC XML | Yes, with a layer when `<w>` is present | No | Reference corpora and scholarly editions |
| GrAF (OANC, MASC) | Yes, with layer | No | Standoff corpora |
| VRT (CWB, Sketch Engine, CQPweb) | No | Yes | Analysis in established corpus software |
| Token table (CSV, JSONL, Parquet) | No | Yes | External statistical analysis, archiving |
| Reference frequency list (`.tsv`) | Yes, as a reference | Yes | Item counts of a corpus, without its texts, for keywords and frequency bands |

An analysis layer can be exported to CoNLL-U or VRT, which other corpus software can read, or to CSV, JSONL (one JSON record per line), or Parquet (a compressed table format used in data analysis), which allow token-level analysis in statistical software and programming environments. The reference frequency list is a tab-separated text file (`.tsv`) that contains no texts, only how many times each form, lemma, or part of speech occurs in a corpus. Its first line holds a description sheet with information such as language, variety, size, and license. The file can be used as a reference in keyword and frequency-band analyses, so it makes it possible to share the results of a corpus that cannot be redistributed, since the license may not allow distributing the texts but may allow distributing statistics derived from them.

As stated before, the project format uses only standard-library resources. This restriction is deliberate. It reduces the risk that a project becomes unreadable when an external library disappears or changes its format. Interoperability with external formats is handled by import and export routes, not by the core of the project file.

### 4.2.8 Catalog, Models, and User Data

The application can work with personal corpora and with reference corpora obtained through a catalog. The **catalog** is a list of packages described in a `catalogo.json` file, a structured text format readable by people and by programs. Each package has a **description sheet** with language, variety, period, genres, size, license, source, available layers, and hashes. The sheet is validated, so that the license is part of the distribution decision.

A package can contain the annotated project, only the frequency lists, or both. For corpora whose license does not allow redistribution of the texts, the format provides for a **recipe** entry instead of a package, which points to the original source so that users can prepare their own copy. This distinction matters for research ethics and for the publication of results. At present, the catalog mechanism is implemented, but no public catalog is configured by default.

spaCy and Stanza models are downloaded on demand and stored in the user’s data folder. On macOS, this folder is `~/Library/Application Support/TTWtools`; on Windows, `%LOCALAPPDATA%\TTWtools`; on Linux, `~/.local/share/TTWtools`. An environment variable can change the location. The models have their own licenses, and the application shows the description sheet and the size before download. MFTE is distributed under the GNU General Public License (GPL) and is an optional dependency with separate legal treatment in distribution. This separation is a technical and legal decision, not only a matter of convenience.

The data folder also stores the cache, settings, and installed packages. The application provides a disk-usage screen with options to clear the cache and abandoned work folders. This addresses a practical problem: analysis of large corpora can generate temporary copies and indexes that occupy a large amount of space.

### 4.2.9 Execution, Performance, and Compatibility

An analysis can take seconds or minutes, depending on corpus size and tagger. TTWtools treats long operations as **tasks**, not as stalled requests. The interface shows progress by stage and allows cancellation. The local server runs the task in the background and reports progress; when the task finishes, the result is displayed. This design prevents the window from appearing frozen and allows the user to continue navigating while the calculation runs.

Before writing, the application checks free disk space. If there is not enough space, the operation is refused before a partial file is created. The check includes a safety margin and a message that states the reason. The application also uses temporary work folders with an owner, the process identifier, so that abandoned folders can be cleaned later. These measures came from real problems. In one development session, temporary copies reached tens of gigabytes.

To ensure broad compatibility, TTWtools runs on macOS 12 or later (Intel and Apple Silicon), Windows, and Linux, with Python 3.11 on Intel Macs and Python 3.14 on Apple Silicon. Automated tests run on all three operating systems at every change.

### 4.2.10 AI Agents and AI Resources in the Project

Two uses of artificial intelligence in this project must be distinguished because they play different roles.

The first is **AI in the product**. TTWtools uses language-processing models, spaCy, Stanza, and MFTE, to tokenize, tag, and lemmatize. These models are machine-learning systems trained on large sets of annotated texts. They are “AI” in the broad sense of the field, but they are not generative models of the kind that produce text in response to a question. The application does not call a generative language service during analysis, does not send texts to the cloud, and does not use user texts to train anything. BiberPlus is based on explicit rules. The choice of which models to use, and transparency about what each one does, is part of the methodological design of the tool.

The second is **AI in the development process**. The application was built with the support of programming agents based on language models. The project’s code repository, the versioned folder that stores the source code, has permanent instructions naming Claude, Gemini, Codex, and DeepSeek as compatible agents. The recorded development path shows sessions with AI agents and handoffs between sessions. These agents are not authors of the project and do not make scientific decisions. They act as assistants for implementation, documentation, review, and testing, under the author’s direction and validation.

The tool is not “an AI that analyzes texts.” It is a corpus analysis tool that uses language-processing models and was developed with the help of agents, so the linguistic object and the method of analysis remain human choices. Each development step was tested and reviewed by the author, which addresses the main risks of this use, such as solutions that look correct but are not, or tests that pass without solving the real problem. There is no generative AI inside the application, and user texts are not sent to AI services, so the application does not depend on a network connection to analyze a corpus.

## 4.3 Functions of TTWtools

### 4.3.1 Scope and Organization

This section describes the functions of TTWtools from the user’s point of view: what each one does, which inputs it accepts, which method it applies, and which limits the user should keep in mind. The application is organized into eight areas: File, Tagging, Explore, Reader, Compare, Writing, Learn, and Resources. As explained in Section 4.2, the same operations are available through the graphical interface, the command line, the Python package, and a local REST API.

Two areas are marked experimental and are still under development: the Lab, for comparisons of several groups, and Writing, for the comparison of a single text with a reference corpus. Their features and interfaces may change, and their results are descriptive or exploratory, as the interfaces state. The remaining functions are part of the stable workflow. The description follows the order of a typical project.

### 4.3.2 Projects and Corpora

The File area creates, opens, and saves projects, saves them under another name, converts them between the file types described in Section 4.2.4 (for example, separating the texts from the project file or bringing them back), and offers maintenance operations: removing obsolete copies of annotations, building the search index, managing the cache, and listing recent files. Older projects are migrated to the current schema when opened, without deleting the original data.

To import a corpus, the user chooses a folder of texts, a file, or pasted text, and names the corpus. Metadata, such as proficiency level, genre, year, or author, can be taken from the filenames, by defining a delimiter and the fields (a name such as `student_B1_2024.txt` yields student, level, and year) after a preview that lets the user correct the pattern, or from a spreadsheet with one row per document. These metadata can then be used to group results in Search and Frequency and to define the groups that are compared in the Compare area. Corpora that are already annotated are imported with their annotation, so they do not need to be tagged again (Section 4.2.7).

The corpus overview describes the corpus before and after tagging. Without a tagger, it uses a simple tokenizer and reports the number of documents, tokens, types, and hapax legomena; the type/token ratio and its variants (corrected, standardized, and moving-average); word and sentence length; the distribution of document sizes; the most frequent words; and the Zipf curve. These values are estimates, because taggers tokenize differently, and the interface states this. With a layer, the overview adds the distribution of tags, lexical density, the most frequent lemmas by part of speech, and the mean and standard deviation of the main tags per 1,000 words across documents, which shows how evenly each tag is distributed.

The pipeline is a list of operations to run on a corpus, such as basic statistics and one or more tagging layers with their options. It is stored in the project, so the user can leave and return later. When it runs, the application calculates only what is missing, shows progress by step and by document, and keeps the work already completed if the run is interrupted. This is useful for large corpora and slow machines, and it records what the user intended to do when the project is reopened.

### 4.3.3 Tagging and Layers

The Tagging area applies the taggers described in Section 4.2.6 to a corpus. The application detects the language of the corpus from its layers or from its function words and suggests a model, which the user can change; BiberPlus and MFTE are limited to English, while spaCy and Stanza have English and Portuguese models. Each tagger has a tag set, which the interface shows with definitions and examples, so that the user can interpret a tag before interpreting a count. The same definitions appear in the Reader and in the Learn area.

Three presets (Fast, Recommended, and Most accurate) fill in the options of a tagger, and the Customize panel exposes each option with an explanation. Options are marked as result-changing, such as the model or the components to extract, or as performance-only, such as batch size, number of processes, and device. Only result-changing options define a new layer. The panel also checks availability: if a spaCy or Stanza model is missing, it offers to download it and shows its size, and if torch is not available on the machine, Stanza and MFTE are marked as unavailable with the reason, so that no run starts that cannot finish.

Before tagging, the application plans the run and reports how many documents already have a sufficient layer, how many can copy a layer from an identical text, and how many will be processed. Each document is saved as it finishes, so an interrupted run continues from where it stopped. The interface lists the layers of a corpus with the tagger, version, model, configuration, number of tokens, and date, and allows exporting a layer or counting the occurrences of each tag. The options and tag sets are also available from the command line (`ttwtools tagger-options` and `ttwtools tagset`), with the same descriptors used by the interface.

### 4.3.4 Exploring a Corpus

The exploration functions (Search, KWIC, Frequency, Collocates, and Dispersion) share the same query language. A query is a sequence of tokens separated by spaces, and each token can be a form (`house`), a form with wildcards (`hous*`) or a regular expression (`/^run(s|ning)$/`), a lemma (`lemma=run`), a part of speech (`pos=NOUN`, `upos=NOUN`, `xpos=NN`), or a tagger tag (`tag=PASS`). Conditions on the same token are combined with `&` (`lemma=run&pos=VERB`), alternatives with `|` (`tag=PASS|NN`), and a phrase is written as consecutive tokens (`black cat`). The interface includes a tag picker that lists the tags of the active layer with their counts. A query is evaluated on a layer; when the user does not choose one, each document uses its most recent layer, and documents without a layer receive a simple one with forms and positions, so that search, frequency, and KWIC work before tagging.

Search counts the occurrences of a query, in total, per document, and per metadata group. KWIC shows each occurrence with its left and right context, which can be resized, with the part of speech of the match, the filename, and the position. The lines can be sorted by position or by the word on either side, and a click opens the Reader at that point. KWIC connects a count to its occurrences, which makes it possible to check whether a pattern found by a statistical measure corresponds to a recurring construction or to a few isolated cases.

Frequency lists the most frequent items by form, lemma, word plus class, class, or n-gram, for the whole corpus, per document, or per metadata group, with absolute frequency and frequency per 1,000 words, and with the option of hiding function words. The choice of unit has consequences: lemma counts group `run` and `running` but require a layer with lemmas, and word plus class separates homographs. The application warns when the chosen unit requires a field that the layer does not have, as in a lemma frequency over a BiberPlus layer.

Collocates finds the words that occur near a node, given a window to the left and to the right, a unit, and a minimum frequency. For each collocate, it reports the observed and expected frequencies, mutual information (MI), the T-score, and log-likelihood, and the user can sort by any of them, and open examples in context. The measures answer different questions: MI shows the strength of the association but is unstable for rare items, the T-score favors frequent collocates, and log-likelihood compares observed and expected frequencies. The application presents them side by side and does not choose one as correct, and it shows the window and the minimum frequency so that the user can report them.

Dispersion shows where a query occurs in each document, and reports the measures of Gries: DP (deviation of proportions), Range, and normalized DP. A DP near zero indicates a uniform distribution, and a value near one indicates a concentrated one. The result can be shown as a heatmap of position bands, a barcode with one tick per occurrence, or tables, and several queries can be compared at once. The measures are descriptive, and they help the user see whether a frequency is spread across the corpus or concentrated in a few texts, which matters for keywords and frequency lists.

The Reader shows a document with its annotation. The user chooses the corpus, the document, and the layer, and a side panel lists the tags with their counts and colors, which can be selected to mark them in the text with different styles (highlight, underline, circle, box, and others). It also offers search with fragments, wildcards, and regular expressions, navigation between matches, copying, printing, zoom, and tooltips with the definition of each tag. The Reader is linked from KWIC, collocate examples, dispersion charts, keyword results, and KFA charts, so that the user can move from a result to the text and back.

### 4.3.5 Comparing Corpora and Groups

The Compare area has a comparison bar that defines the two sides of an analysis: side 1 is the active corpus, and side 2 can be another corpus in the project or a second group of the same corpus, defined by metadata. The bar applies to Keywords, KFA, Frequency bands, the Lab, and the dispersion comparison. The layer follows the one chosen at the top of the screen, and the interface warns when a result refers to a previous layer or when the chosen unit requires a field that the layer does not have. The analyses report the number of texts and words on each side, since the sides can differ in size.

Keywords compares a target corpus or group with a reference, which can be another corpus in the project, a group of the same corpus, a `.tsv` frequency list, or a list installed from the catalog. The user chooses the unit (form, lemma, part of speech, word plus class, or n-gram), the measure used for ordering, minimum frequency, the minimum number of target texts in which an item appears, and the correction for multiple comparisons (Bonferroni, false discovery rate, or none). The measures are log-likelihood (LL), which expresses the evidence that the difference is not due to chance; log ratio, %DIFF, and log-odds, which express the size of the difference. For each item, the result reports the frequencies on each side, the number of texts, the measures, the raw and adjusted p-values, and the direction, and a click opens KWIC for the item. The analysis also warns about problems of comparability, such as different languages, different taggers or versions, small corpora, or a missing lemma field. The interpretation requires both evidence and size: a high LL with a small log ratio is a frequent item with a small difference, and a high log ratio with a low frequency may be an item that occurs only once or twice, which should be checked in KWIC.

Key Feature Analysis (KFA) compares two corpora or groups by their linguistic features, which are the tags, UPOS, or XPOS of a layer. The application builds a table with one row per document and one column per feature, with counts per 1,000 words, and calculates Cohen’s d for each feature between the two sides. The metric can be KFA, which uses the pooled standard deviation of Biber and Egbert, or wKFA, which weights the standard deviation by the number of texts on each side and is preferable when the sides differ in size. The user sets a minimum absolute d, which filters the result without recalculating the counts. The result is shown as a table, sortable by feature, effect size, or count, and as a gallery of charts (diverging bars, scatter plots, violin plots, heatmaps, radar charts, and dimension reductions such as PCA, t-SNE, MDS, and UMAP). A click on a feature lists the texts in which it occurs, and a click on a text opens the Reader. KFA requires at least two documents on each side, and the effect size is descriptive: it shows how far the sides are, in standard deviation units, and does not by itself establish statistical significance.

Frequency bands describe how much of a target text is made of the most frequent words of a reference, following the lexical frequency profile of Laufer and Nation. The user chooses a reference (a frequency list, a corpus in the project, or a list from the catalog), a unit, and the band limits, which by default are the first 1,000, 2,000, 3,000, 5,000, and 10,000 words, plus an off-list band. For each band, the result reports the number and percentage of tokens and types, with examples. The interpretation depends on the reference and on the tokenization: a general reference shows how much of the text uses common vocabulary, while a reference from the same genre shows finer differences.

The Lab, which is experimental, compares two or more groups, defined as corpora or as subsets of a corpus by metadata, using the same document by feature table as KFA. Its methods are one group against all the others (Cohen’s d per feature), pairwise comparisons with a distance matrix, a global test per feature (Kruskal-Wallis, with epsilon squared and adjusted p), a profile space (PCA of the texts), a dendrogram of the groups (hierarchical clustering with Ward linkage), and the nearest group. The Lab warns when a group has fewer than five documents, and about multiple comparisons and unequal group sizes, and its results are exploratory.

The dispersion comparison applies the dispersion measures to the two sides of the comparison bar, with a panel for each side, showing the position of the query in each text, which can be sorted by name, frequency, or contributed DP. It is descriptive: it shows whether a query is more concentrated in one side and in which texts, without testing the difference between the two values.

### 4.3.6 Writing

The Writing area, which is experimental, compares one text with a reference corpus. The text is one unit, not a random sample of independent units, so the results are descriptive and exploratory, and the interface states this in a note on how to read them. The user pastes a text or uploads a file (`.txt`, `.md`, `.docx`, `.odt`, and PDF when the optional `pypdf` package is installed), and the reference can be a corpus in the project, a `.tsv` frequency list, or a list from the catalog.

The Words tab performs a keyword analysis of the text against the reference, by default with forms, log ratio, and false discovery rate correction. Besides the usual measures, it reports the dispersion of each item in the reference and a z-score that compares the rate in the text with the distribution of rates across the reference documents. Reliability flags mark rows with less support, such as items that are rare in the text, concentrated in few reference texts, or not significant after correction, and the flags tell the reader how much confidence to place in each row. The results can be explored in a table, in a diverging bar chart, and in examples in the text and in the reference, with the classes colored; when the reference is a project corpus, the action `See in corpus` opens KWIC in the reference, which supports data-driven learning.

The Constructions tab compares the patterns of the text with those of the reference, where a pattern is an n-gram of UPOS or XPOS, such as determiner, adjective, noun, following the operational side of pattern grammar. The reference must be a corpus in the project tagged with spaCy, because the text is tagged on the fly with the same model and the class inventories must be comparable. Each pattern receives the same measures as the keywords and the same flags. The collocate profile compares the collocates of a node in the text with those in the reference, marking collocates that occur only in the text and those that are typical of the reference, which makes visible differences in combinability even when the frequency of the word is the same. The lexical profile reports descriptive measures of vocabulary and sentences, such as the number of words and types, the type/token ratio, the Guiraud index, the Measure of Textual Lexical Diversity (MTLD), the mean sentence length, and the percentage of long words, without comparing the text with a norm. In all tabs, the user should look at the frequency and the effect size together and check the occurrences before drawing conclusions.

### 4.3.7 Learning and Help

The Learn area contains explanations of concepts, methods, metrics, and screens, such as Cohen’s d, dispersion, frequency bands, and normalization per 1,000 words. The topics are organized by area and searchable, and the same content feeds the tooltips next to metrics, the `Explain this screen` action, the guided tours, and the `ttwtools help` command. Formulas are rendered with KaTeX, and the KFA topic includes an interactive widget for Cohen’s d. The guided tours show a sequence of steps over the interface, and the tag set drawer shows the definitions of the tags of each tagger. The content is available in Portuguese and English, and a command (`ttwtools help --check`) validates the topics, reporting missing titles and broken links.

### 4.3.8 Resources

The Resources area manages corpora and models. It installs, removes, updates, and validates the packages of a catalog (Section 4.2.8), shows the description sheet before installation so that the user can judge whether the corpus and its license fit the research question, and lists the installed packages and the available reference lists. The public catalog address has not been defined yet, so the user provides a catalog URL or a local `catalogo.json` file.

Models of spaCy and Stanza are downloaded on demand, from the interface or with `ttwtools catalog download-model`, and stored in the user’s data folder, which can be changed with the `TTWTOOLS_DATA_DIR` variable. The area lists each model with language, size, source, license, and training data, and shows whether it is installed and whether it can run on the current machine. MFTE is an optional dependency under the GNU General Public License, and its distribution is treated separately. The disk-usage screen shows the size of the index cache, the work folders, and the free space, and allows clearing the cache and the abandoned folders. The application also removes stale folders at startup, limits the size of the cache, and warns before operations that need more disk space than is available.

### 4.3.9 Automation and Interoperability

The command line exposes the same functions as the interface, from import and tagging to search, KWIC, frequency, collocates, dispersion, keywords, KFA, frequency bands, and Writing. Each command accepts a project path, a corpus name, a layer, metadata filters, and the parameters of the analysis, and returns a table, JSON, or CSV. It does not depend on the graphical interface, but it uses the same project files and the same package functions. Most analyses in the interface have a `Copy as code` action that produces the equivalent command and a Python snippet with only the parameters the user set, so that a reader of a thesis or an article can see the command that produced a table or a chart, and a collaborator can rerun it on the same data.

The Python package exposes the same operations as public functions, which return dictionaries or DataFrames, and imports heavy dependencies only when needed, so `import ttwtools` is fast. A typical script is:

```python
import ttwtools

with ttwtools.open_project("project.ttwa") as proj:
    ttwtools.tag_corpus(proj, "essays", "spacy", preset="recommended")
    result = ttwtools.keywords(proj, "essays", "catalog:brown", unit="lemma")
    print(result["rows"][:10])
```

The interface communicates with a local FastAPI server, whose routes validate the parameters and call the package functions, and run long operations (tagging, opening large projects, saving, KFA) as jobs with progress and cancellation. The server is local, not a public web service, and requires no account. It can be used for integration with other software, but the recommended path for scripts is the Python package or the command line, because the routes may change more often than the public functions.

Tables can be exported as CSV or TXT, and charts as SVG or PNG, and an exported table corresponds to the current view, so that a filtered table exports the filtered rows. Layers can be exported as CoNLL-U, VRT, CSV, JSONL, or Parquet, reference lists as `.tsv` files with a description header, and the corpus texts to a folder next to the project (Section 4.2.7).

### 4.3.10 Cross-Cutting Features

The interface is available in Portuguese and English, and its language is independent of the language of the corpus: a user can analyze an English corpus with a Portuguese interface, or the reverse. The interface language controls menus, messages, help, tag definitions, and chart labels, but the application does not translate the corpus or the user’s texts. The corpus language controls the tagger and the model.

The interface offers light, dark, and high-contrast themes, among other visual options, with fonts bundled with the application, so that the appearance does not depend on the system. It is designed for keyboard use and for screen readers, with labels, visible focus, and a table alongside each main chart, and the end-to-end tests include automated accessibility checks, which catch common problems but do not prove full conformance with a standard.

The application runs on the local machine and works offline once the resources are installed; models and corpora are downloaded only when the user asks. Long operations run as tasks with progress and cancellation, and the application checks free disk space before writing. It records the layers and the parameters used by each analysis, which supports reproducibility and helps the user understand why a result changed after a new layer was added.

### 4.3.11 Summary

The functions described in this section follow the order of a research project: the user creates a project and imports a corpus, tags it with one or more taggers, explores it with searches, concordances, frequency lists, collocates, and dispersion measures, compares corpora and groups, analyzes a single text against a reference, and automates the analysis through the command line or the Python package. The measures describe the corpora; they do not turn a corpus into a random sample of a population. Keywords, KFA, frequency bands, dispersion, and Writing report differences, effect sizes, and dispersion, and the interface states this where it matters, while the help topics explain the assumptions and the cautions.
